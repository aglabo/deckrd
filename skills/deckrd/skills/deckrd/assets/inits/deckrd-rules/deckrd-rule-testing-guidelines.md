## Deckrd Rule: テストコード規約 (汎用)

TEST は設計チェーンの成果物とする。検証内容は TEST ドキュメントが定義するが
（[ドキュメントモデル](deckrd-rule-document-model.md) 参照）、それを実装する
テストコードの構造にも規約を置く。

言語・テストフレームワークは問わない。以下では説明のため BDD スタイルの
`describe`/`it` を用いる。`context`/`test`、`Feature`/`Scenario`、
テーブル駆動テストなど、各言語の同等構文に読み替えること。

## 1. グループとケースの階層原則

- グループ (`describe` 相当) = 機能・シナリオのまとまり
- ケース (`it` 相当) = 単一の振る舞いだけを検証する

1 ケースが複数の振る舞いをまとめて検証すると、失敗時にどの振る舞いが壊れたのか
テスト名から特定できなくなる。

## 2. テーブル駆動テストのループ位置

**ケースを生成するループは、グループの内側・ケースの外側に置く。**

```text
Good — ループがケースを生成する (失敗したケースが名前で特定できる)

  group "normalize"
    for (input, expected) in cases
      case "normalize({input}) -> {expected}"
        assert normalize(input) == expected

Bad — ケースの内側でループする (どの入力で落ちたか分からない)

  group "normalize"
    case "all cases pass"
      for (input, expected) in cases
        assert normalize(input) == expected
```

生成される各ケースの名前には、ケース識別子と入出力値を埋め込む。

集合全体の性質を 1 回で比べるアサーション (例: 抽出した ID 列の重複が 0 件) は、
ケースの内側のループに当たらない。Bad 例は、入力ごとの期待値をケースの内側で順に確かめる形を指す。

## 3. テストデータの定義場所

テストデータ (ケース配列・フィクスチャ) は、テストケースの内側にも
ファイルのトップレベルにも直書きしない。テストファイル内の内部ヘルパー領域に
まとめて定義する。

- 内部ヘルパーであることが名前から分かるようにする
  (言語の慣習に従う。例: 先頭アンダースコア、`private`、ローカルスコープ)
- 同じデータを複数のグループが参照する場合も、定義は 1 箇所に保つ

内部ヘルパーの命名は [Coding Guidelines](deckrd-rule-coding-guidelines.md) の
「内部シンボルの命名」に従う。

## 4. 階層と分類ラベル

テストは 4 階層を基本とする。Given は省略し、対象 → 機能 → 分類 → ケースの順に整理する。

| 階層   | 内容                           | 名前の例                                       |
| ------ | ------------------------------ | ---------------------------------------------- |
| 対象   | テスト対象のクラス・関数       | `GlobalConfig` / `normalize`                   |
| 機能   | メソッド・機能の単位           | `<グループ ID>: getInstance`                   |
| 分類   | 正常系 / 異常系 / エッジケース | `When: 正常系`                                 |
| ケース | 単一の振る舞い                 | `[Normal] <ケース ID>: 2 回目は同一参照を返す` |

**機能階層のグループがテスト ID を宣言する。** 対象階層と分類階層のグループは
ID を持たない（[5. テスト ID](#5-テスト-id) 参照）。

分類は 3 種類とし、ケース名の先頭に対応する prefix を付ける。

| 分類         | 分類グループ名       | ケース名の prefix |
| ------------ | -------------------- | ----------------- |
| 正常系       | `When: 正常系`       | `[Normal]`        |
| 異常系       | `When: 異常系`       | `[Error]`         |
| エッジケース | `When: エッジケース` | `[Edge]`          |

```text
group "GlobalConfig"                     -- 対象
  group "T-CFG-GI: getInstance"          -- 機能（グループ ID を宣言する）
    group "When: 正常系"                 -- 分類
      case "[Normal] T-CFG-GI-01: 2 回の取得は同一参照を返す"
    group "When: 異常系"
      case "[Error] T-CFG-GI-04: 不正な設定 -> 設定エラーを送出する"
```

分類が 1 種類しかない場合は分類階層を省略し、機能の直下にケースを置いてよい。
その場合もケース名の prefix は省略しない。

対象が 1 個しかなく機能階層を別に立てない場合は、最上位のグループがグループ ID を持つ。

## 5. テスト ID

テストに関わる ID は 2 層ある。混同してはならない。

| 層                | ID 書式    | 宣言場所                            | 参照するもの                          |
| ----------------- | ---------- | ----------------------------------- | ------------------------------------- |
| TEST ドキュメント | `TEST-XXX` | `test-NNN-<slug>.md` の frontmatter | 設計チェーン、コミット本文            |
| テストコード      | `T-...`    | テストコードのグループ名・ケース名  | テスト実行結果、TEST ドキュメント本文 |

`TEST-XXX` の採番は [ドキュメントモデル](deckrd-rule-document-model.md) が正とする。
コミット本文が参照する Test ID は `TEST-XXX` であり、本節のテスト ID ではない。
1 個の `TEST-XXX` は複数のテスト ID を束ねる。

以下にテストコードのテスト ID の規約を示す。

### 5.1 書式

テスト ID はグループ ID とケース ID の 2 段からなる。
**採番の単位はグループ ID であり、ケース ID はその中の連番にすぎない。**

```text
グループ ID   T-<scope>-<target>
ケース ID     T-<scope>-<target>-<連番>[-<枝番>]
```

| セグメント | 内容                              | 一意性の範囲       |
| ---------- | --------------------------------- | ------------------ |
| `scope`    | モジュールが宣言する `test_scope` | 宣言リポジトリ全体 |
| `target`   | テスト対象の関数・クラスの略語    | モジュール内       |
| 連番・枝番 | 2 桁ゼロ埋め                      | グループ内         |

- `scope` は大文字英数 2〜4 文字とする
- `target` は大文字英数とする
- **グループ ID は機能階層のグループ名の先頭に置く。** 書式は `<グループ ID>: <名前>`
- **ケース名の先頭に必ずケース ID を埋め込む。** 分類 prefix の直後に置く

```text
group "T-CFG-GI: getInstance"
  case "[Normal] T-CFG-GI-01: 2 回の取得は同一参照を返す"
```

同一対象を複数のレイヤで検証する場合は、レイヤごとに別の略語を割り当てる
（例: unit を `GI`、integration を `GII`、functional を `GIF`）。
**`target` は綴り全体で 1 個の略語とする。** 末尾の文字をレイヤの印として
切り離してはならない。`CINI` は `CIN` + `I` ではなく `CINI` の 1 語とする。

### 5.2 スコープはモジュールが宣言する

`scope` を書くたびに未使用かを全テストから探してはならない。
**モジュールが自分の `scope` を宣言し、テスト ID はその宣言から導く。**

モジュールの `workspaces/modules/module.md` が宣言を持つ
（配置は [ドキュメントモデル](deckrd-rule-document-model.md) 参照）。

```yaml
---
title: normalize
test_scope: NC
owns:
  - src/normalize/**
---
```

| フィールド   | 必須 | 内容                                                              |
| ------------ | ---- | ----------------------------------------------------------------- |
| `test_scope` | 必須 | テスト ID の第 1 セグメント。宣言リポジトリ内で一意               |
| `owns`       | 必須 | このモジュールが所有するソース・テストのルート（glob 可・複数可） |

`owns` を省いてはならない。所有関係が引けないと、モジュール単位の検査も、
どのモジュールにも属さないテストファイルの検出もできなくなる。

本文にはモジュールの概要と、割り当て済みの `target` 略語の対応
（例: `GI = getInstance`）を書く。**連番の台帳は書かない。**
連番は実体から導出する（[6. テスト ID の機械検査](#6-テスト-id-の機械検査)）。

略語の対応は「テスト対象の略語」という見出しの下に、次の 2 列の表で書く。
見出しと列は機械検査 D が読むため、書式を変えてはならない。

```markdown
## テスト対象の略語

| 略語 | 対象          |
| ---- | ------------- |
| `GI` | `getInstance` |
```

**表にはテストが使う略語を、綴りのまま 1 行ずつ書く。** `GI` を unit で、`GII` を
integration で使っているなら、表は `GI` と `GII` の 2 行になる。綴りを分解して
1 行にまとめてはならない（[5.1](#51-書式)）。

### 5.3 モジュールを持たないリポジトリ

Deckrd のモジュール構成を採らないリポジトリは、リポジトリに 1 本の宣言表を置く。
フィールドの意味は `module.md` と同じであり、行が `module.md` 1 個分に対応する。

| `test_scope` | 対象               | `owns`          |
| ------------ | ------------------ | --------------- |
| `LIB`        | 共有ライブラリ     | `src/libs/**`   |
| `CFG`        | 設定クラス         | `src/config/**` |
| `CLI`        | コマンドライン入力 | `src/cli/**`    |

宣言の置き場所が違うだけで、以降の規約と検査は module.md の場合と同一とする。

### 5.4 一意性の範囲

**同一のテスト ID を 2 つ以上の宣言に割り当ててはならない。** テスト種別が違っても
同じ制約がかかる。ID だけでテストを一意に特定できることを、この規則の目的とする。

これを次の 5 つの局所的な規則に分解する。すべてを守れば全体の一意性が従う。

| 規則           | 内容                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------- |
| scope 一意性   | `test_scope` は宣言リポジトリ内で一意であり、全テストがちょうど 1 つのモジュールに所有される |
| scope 整合性   | モジュールが所有するファイル内のグループ ID は、そのモジュールの `test_scope` で始まる       |
| グループ一意性 | グループ ID は宣言リポジトリ内で一意であり、2 つのグループが同じ ID を名乗らない             |
| ケース所属     | ケース ID は、そのケースを囲む機能階層のグループが宣言するグループ ID で始まる               |
| 連番一意性     | 同一グループ内で連番・枝番が重複しない                                                       |

scope 整合性が抜けると分解が成り立たない。あるモジュールのファイルが他モジュールの
`scope` を名乗ると、どちらのモジュール内でも重複が 1 回ずつにしか見えず、
検査をすり抜ける。

ケース所属と連番一意性が抜けても分解が成り立たない。グループ ID が一意でも、
ケースが自分のグループ外の ID を名乗れば、その ID は他のグループのケースと衝突しうる。

この 5 つが満たされている限り、**新しいテストを書くときに見るのは自モジュールの
`owns` 配下だけでよい。** 他モジュールの ID を調べる必要はない。
連番に至っては、見るのは自分が書いているグループの中だけでよい。

`target` はファイル単位ではなくテスト対象の関数・クラス単位で決める。
**1 個の `target` には 1 個のグループだけが対応する。** 同じ `target` を
複数のグループが名乗ることはできない。

ドキュメントコメントから他ファイルのテスト ID を参照するのは構わない。
ここでいう「割り当て」とは、グループ名とケース名に書かれた ID だけを指す。

## 6. テスト ID の機械検査

prefix 一覧や ID 台帳を人手で維持してはならない。実体から導出する。
この原則は [ドキュメントモデル](deckrd-rule-document-model.md) の重複検出と同じ考え方に従う。
本節はテスト ID 固有の注意点だけを定める。

検査は 4 つに分かれる。A・B が [5.4](#54-一意性の範囲) の 5 規則を分担し、
C はそこから従う全体の一意性を最終ゲートで確かめる。D は `target` 略語の台帳が
実体と一致していることを確かめる。

| 検査 | 内容                                          | 走査範囲                       | 実行する場面     |
| ---- | --------------------------------------------- | ------------------------------ | ---------------- |
| A    | scope 一意性・書式と所有網羅性                | 宣言ファイルとテストファイル名 | 常時             |
| B    | ID 付与網羅性・ケース所属・連番・scope 整合性 | そのモジュールの `owns` 配下   | テストを書いた後 |
| C    | リポジトリ全体のグループ ID 重複              | 全テストファイル               | CI の最終ゲート  |
| D    | 略語表と実体の一致                            | そのモジュールの `owns` 配下   | テストを書いた後 |

### 6.1 抽出パイプライン

グループ ID とケース ID は別の宣言行から抽出する。**両者を混ぜてはならない。**
グループ ID はケース ID の prefix であり、同じパターンで両方を拾おうとすると、
どちらの検査も意味を失う。

```bash
# 1) グループ宣言に割り当てられた ID を抽出する
grep -rho '<グループ宣言のパターン>' <テストファイルの検索条件> <走査範囲> \
  | tr -c 'A-Za-z0-9-' '\n' \
  | grep -xE 'T-[A-Z0-9]{2,4}-[A-Z0-9]+' \
  | sort > <グループ ID の一時ファイル>

# 2) ケース宣言に割り当てられた ID を抽出する
grep -rho '<ケース宣言のパターン>' <テストファイルの検索条件> <走査範囲> \
  | tr -c 'A-Za-z0-9-' '\n' \
  | grep -xE 'T-[A-Z0-9]{2,4}-[A-Z0-9]+-[0-9]{2}(-[0-9]{2})?' \
  | sort > <ケース ID の一時ファイル>

# 3) 総数と異なり数を数える
total=$(wc -l < <一時ファイル>)
unique=$(sort -u <一時ファイル> | wc -l)
```

**重複検査はこの 2 つの数の比較で行う。**

| 判定                | 意味                       |
| ------------------- | -------------------------- |
| `total` が 0        | パイプラインが途中で壊れた |
| `total` != `unique` | 重複がある                 |
| `total` == `unique` | 合格                       |

`uniq -d` を検査の本体にしてはならない。この方法はソート済みで重複が隣接して
いることを前提にしており、抽出結果の並べ方に検査の正しさが依存する。数を比べる
方法は並び順に依存せず、同じ 2 つの数で「抽出が 0 件」も同時に捕えられる。
**件数の確認と重複検査は同じ 1 手で済む。**

`uniq -d` は重複が見つかった後、どの ID かを挙げるためだけに使う。
検査を失敗させる判断は、あくまで数の比較で下す。

`total` が想定より極端に少ないときは、出力が途中で打ち切られている
（コマンドプロキシは大量ヒット時に出力を切り詰めることがある。切り詰めを知らせる行は
後段の `grep` で捨てられるため、件数を見ないと気づけない）。

標準エラー出力を捨ててはならない。握り潰すと「重複なし」と区別が付かなくなる。

次の 3 点を外すと、検出漏れ・誤検出を起こす。

- 抽出対象を宣言の行に限定する。限定しないと、コメント中の相互参照を割り当てと誤認する
- トークン境界で照合する（区切り文字で分割してから完全一致させる）。しないと、
  prefix 付き ID の内部一致を prefix なしの ID と誤認する。
  グループ ID とケース ID を取り違えないのも、この完全一致が担保する
- ファイル単位で一意化してから集計しない。同一ファイル内の重複を取りこぼす。
  割り当ての出現回数を、全ファイル横断で数える

ケース所属（[5.4](#54-一意性の範囲)）を検査するには、ケース ID がどのグループの下に
あったかも要る。**グループの入れ子を追う必要はない。** 宣言は上から順に現れるので、
ファイルを 1 度なぞり、直前に現れたグループ ID を覚えておけばよい。

### 6.2 検査 A: scope 一意性と所有網羅性

宣言ファイルだけを走査する。テストコードは読まない。

1. 全モジュールの `test_scope` を集め、書式が `^[A-Z0-9]{2,4}$` であり、
   かつ重複が無いことを確認する
2. 全テストファイルを列挙し、それぞれが **ちょうど 1 つ** のモジュールの `owns` に
   一致することを確認する

どのモジュールにも属さないファイルと、2 つ以上のモジュールに属するファイルは、
どちらも 5.4 の分解を壊す。0 件でなければならない。

### 6.3 検査 B: ID 付与網羅性・ケース所属・連番・scope 整合性

対象モジュールの `owns` 配下だけを 6.1 で抽出し、次の 5 つを確認する。

- **ケース宣言の行がすべて ID を持つこと。** 6.1 の抽出は書式に合わないトークンを
  捨てるので、ID を持たない宣言と書式の壊れた ID は、抽出結果からは区別できず
  どちらも「無かったこと」になる。抽出とは別に、ケース宣言の行を数え直し、
  ID を 1 つも持たない行を列挙する
- **各ケース ID が、直前に現れたグループ ID で始まること。** 一致しない行は、
  グループ ID の付け忘れか、ケースの置き場所の誤りである。直前のグループが
  1 つも無い位置にあるケースも、同じくエラーとする
- グループ ID の総数と異なり数が一致すること
- ケース ID の総数と異なり数が一致すること（同一グループ内の連番衝突を捕える）
- 抽出した全グループ ID の第 1 セグメントが、そのモジュールの `test_scope` と一致すること

**抽出結果の検査だけで網羅性を担保できない。** 1 個でも正しい ID があれば
後続の検査が通ってしまう。総数が 0 でも総数と異なり数は一致してしまう。
ID の付け忘れと書式違反は、必ず宣言の行そのものを見て検出する。

テストを書いた直後はこれを実行する。全リポジトリを走査する必要はない。

### 6.4 検査 C: リポジトリ全体のグループ ID 重複

全テストファイルからグループ ID を 6.1 で抽出し、総数と異なり数が一致することを
確認する。

**ケース ID を全件照合する必要はない。** グループ ID が全体で一意であり（本検査）、
かつ各ケースが自分のグループに属し連番が重複しなければ（検査 B）、
ケース ID の全体一意性はそこから従う。照合すべきは採番の単位であるグループ ID だけとする。

A と B が通っていれば C も通る。C は分解の前提が崩れていないことを確かめる
最終ゲートであり、A・B の代わりにはならない。

重複が報告されたら、その ID で再検索して宣言箇所を特定する。

### 6.5 検査 D: 略語表と実体の一致

`module.md` の略語表（[5.2](#52-スコープはモジュールが宣言する)）は、そのモジュールの
テストが実際に使う `target` 略語と過不足なく一致していなければならない。

対象モジュールの `owns` 配下からグループ ID を 6.1 で抽出し、次の手順で突き合わせる。

1. 各グループ ID の第 2 セグメントを、綴りのまま取り出す
2. 得られた略語の集合と、略語表の「略語」列の集合を比較する

**綴りを分解してはならない**（[5.1](#51-書式)）。グループが採番の単位なので、
ケース ID ではなくグループ ID を見る。ケース ID から取り出しても同じ集合になるが、
1 グループにつき 1 回だけ数えるほうが、重複の意味が明確になる。

不一致は 2 方向ある。どちらもエラーとし、検査を失敗させる。

| 種別   | 内容                                   | 意味                         |
| ------ | -------------------------------------- | ---------------------------- |
| 未記載 | テストが使っているが表に無い略語       | 台帳が実体に追いついていない |
| 未使用 | 表にあるがどのテストも使っていない略語 | 削除されたテストの残骸である |

## 7. テストファイルの構成順序

テストファイルは、区切りコメントで示した 5 セクションを決まった順序で並べる。
グループ間は空行 1 行で区切る。

| 順序 | セクション   | 内容                                                 |
| ---- | ------------ | ---------------------------------------------------- |
| 1    | テスト基盤   | テストフレームワーク・アサーション・モックの取り込み |
| 2    | テスト対象   | テスト対象の関数・クラス・定数の取り込み             |
| 3    | ヘルパー     | 検証に必要な補助関数・共有ライブラリの取り込み       |
| 4    | 内部ヘルパー | このファイル内でのみ使う定数・型・関数・スタブの定義 |
| 5    | テスト本体   | テストグループの定義                                 |

- セクション 1〜3 は、言語の取り込み構文（import 相当）をこの順に並べる
- 型・定数・スタブが混在する場合は、1 行コメントを付けたサブブロックに分ける
- セクション 4 は `定数` / `型` / `関数` のサブブロックに分ける
- 不要なセクション・サブブロックは省略してよい

```text
--- テスト基盤 ---
  アサーション / テストグループ・ケース定義 / モック

--- テスト対象 ---
  テスト対象の関数・クラス

--- ヘルパー ---
  補助関数
  # 定数
  # 型

--- 内部ヘルパー ---
  # 定数
  # 型
  # 関数

--- テスト本体 ---
  group "..."
```

## 8. 内部ヘルパーのドキュメントコメント

内部ヘルパーのシンボルには、言語のドキュメントコメント記法で説明を付ける。
何のためのヘルパーかが分からないと、既存ヘルパーが再実装される。

| 対象         | 分量                                      | 記載内容                             |
| ------------ | ----------------------------------------- | ------------------------------------ |
| 定数・スタブ | 1 行                                      | 値の意味と、どのケースで使うか       |
| 関数         | 複数行（引数・戻り値を明記）              | 役割、前提となる状態、引数、戻り値   |
| クラス       | 本体・コンストラクタ・各メソッドの 3 箇所 | 何を差し替えるモックか、各操作の結果 |

テストグループにもドキュメントコメントを付ける。

| 階層 | 分量   | 記載内容                           |
| ---- | ------ | ---------------------------------- |
| 対象 | 複数行 | 対象の責務                         |
| 機能 | 複数行 | 機能の責務、検証するシナリオの概要 |
| 分類 | 1 行   | その分類が何を指すか（省略可）     |

**割り当てたテスト ID の範囲をコメントに書いてはならない。** グループ ID は
グループ名が宣言しており、連番は実体から導出する（[5.2](#52-スコープはモジュールが宣言する)）。
コメントに書いた範囲は更新されなくなり、実体と静かに乖離する。

## 9. テストファイル名

```text
<テスト対象名>.<テスト種別>.<テストファイルの拡張子>
```

テスト種別は次の 5 つを使う。

| テスト種別  | 検証する範囲                 |
| ----------- | ---------------------------- |
| unit        | 単一の関数・クラス           |
| functional  | 機能単位の振る舞い           |
| integration | 複数モジュールの結合         |
| e2e         | 入口から出口までの一連の流れ |
| system      | 実行環境を含めた全体         |

```text
period-filter.unit.spec.<ext>
parse-session.functional.spec.<ext>
find-sessions.integration.spec.<ext>
main.e2e.spec.<ext>
```

テスト種別ごとの配置場所は、プロジェクトの慣習に従う。

## Common Rationalizations

| 言い訳                                   | 反論                                                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 1 ケースにまとめた方がテストが速く書ける | 失敗時にどの振る舞いが壊れたか分からず、デバッグ時間が書いた時間を上回る                         |
| ループはケースの中でも動く               | 動くが、最初の失敗で止まり残りのケースが検証されない。網羅性が失われる                           |
| テストデータは使う場所の近くが読みやすい | 同じデータが複数箇所に複製され、片方だけ更新されて静かに乖離する                                 |
| テスト ID は後からまとめて振ればよい     | 後から振ると既存 ID との衝突検査をやり直すことになる。書いた時点で振る                           |
| 重複検査は `uniq -d` が空なら合格        | `uniq -d` は重複が隣接していることに依存する。総数と異なり数を比べれば並び順に依存しない         |
| ケース名に ID があるならグループ名は不要 | 採番の単位はグループである。グループが名乗らないと、連番の衝突検査をどの範囲で行うかが決まらない |
| 略語の末尾の文字はレイヤなので落とせる   | 綴りから推測すると `CINI` を `CIN` + `I` と誤分解する。略語は綴り全体で 1 個とする               |

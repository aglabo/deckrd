## Deckrd Rule: テストコード規約 (汎用)

TEST は設計チェーンの成果物とする。検証内容は TEST ドキュメントが定義するが
（[ドキュメントモデル](deckrd-rule-document-model.md) 参照）、それを実装する
テストコードの構造にも規約を置く。

言語・テストフレームワークは問わない。以下では説明のため BDD スタイルの
`describe`/`it` を用いる。`context`/`test`、`Feature`/`Scenario`、
テーブル駆動テストなど、各言語の同等構文に読み替えること。

## 1. グループとケースの階層原則

- グループ (`describe` 相当) = 機能・シナリオのまとまり
- ケース (`it` 相当) = 単一の振る舞いだけを検証する

1 ケースが複数の振る舞いをまとめて検証すると、失敗時にどの振る舞いが壊れたのか
テスト名から特定できなくなる。

## 2. テーブル駆動テストのループ位置

**ケースを生成するループは、グループの内側・ケースの外側に置く。**

```text
Good — ループがケースを生成する (失敗したケースが名前で特定できる)

  group "normalize"
    for (input, expected) in cases
      case "normalize({input}) -> {expected}"
        assert normalize(input) == expected

Bad — ケースの内側でループする (どの入力で落ちたか分からない)

  group "normalize"
    case "all cases pass"
      for (input, expected) in cases
        assert normalize(input) == expected
```

生成される各ケースの名前には、ケース識別子と入出力値を埋め込む。

## 3. テストデータの定義場所

テストデータ (ケース配列・フィクスチャ) は、テストケースの内側にも
ファイルのトップレベルにも直書きしない。テストファイル内の内部ヘルパー領域に
まとめて定義する。

- 内部ヘルパーであることが名前から分かるようにする
  (言語の慣習に従う。例: 先頭アンダースコア、`private`、ローカルスコープ)
- 同じデータを複数のグループが参照する場合も、定義は 1 箇所に保つ

内部ヘルパーの命名は [Coding Guidelines](deckrd-rule-coding-guidelines.md) の
「内部シンボルの命名」に従う。

## 4. 階層と分類ラベル

テストは 4 階層を基本とする。Given は省略し、対象 → 機能 → 分類 → ケースの順に整理する。

| 階層   | 内容                           | 名前の例                                       |
| ------ | ------------------------------ | ---------------------------------------------- |
| 対象   | テスト対象のクラス・関数       | `GlobalConfig` / `normalize`                   |
| 機能   | メソッド・機能の単位           | `getInstance` / `期間フィルタ`                 |
| 分類   | 正常系 / 異常系 / エッジケース | `When: 正常系`                                 |
| ケース | 単一の振る舞い                 | `[Normal] <テスト ID>: 2 回目は同一参照を返す` |

分類は 3 種類とし、ケース名の先頭に対応する prefix を付ける。

| 分類         | 分類グループ名       | ケース名の prefix |
| ------------ | -------------------- | ----------------- |
| 正常系       | `When: 正常系`       | `[Normal]`        |
| 異常系       | `When: 異常系`       | `[Error]`         |
| エッジケース | `When: エッジケース` | `[Edge]`          |

```text
group "GlobalConfig"                     -- 対象
  group "getInstance"                    -- 機能
    group "When: 正常系"                 -- 分類
      case "[Normal] T-CFG-GI-01: 2 回の取得は同一参照を返す"
    group "When: 異常系"
      case "[Error] T-CFG-GI-04: 不正な設定 -> 設定エラーを送出する"
```

分類が 1 種類しかない場合は分類階層を省略し、機能の直下にケースを置いてよい。
その場合もケース名の prefix は省略しない。

## 5. テスト ID

テストに関わる ID は 2 層ある。混同してはならない。

| 層                | ID 書式    | 宣言場所                            | 参照するもの                          |
| ----------------- | ---------- | ----------------------------------- | ------------------------------------- |
| TEST ドキュメント | `TEST-XXX` | `test-NNN-<slug>.md` の frontmatter | 設計チェーン、コミット本文            |
| テストケース      | `T-...`    | テストコードのケース名              | テスト実行結果、TEST ドキュメント本文 |

`TEST-XXX` の採番は [ドキュメントモデル](deckrd-rule-document-model.md) が正とする。
コミット本文が参照する Test ID は `TEST-XXX` であり、本節のテストケース ID ではない。
1 個の `TEST-XXX` は複数のテストケース ID を束ねる。

以下にテストケース ID の規約を示す。

### 書式

```text
T-<スコープ>-<対象略語>-<連番>[-<枝番>]
```

- 連番・枝番は 2 桁ゼロ埋め
- **ケース名の先頭に必ず ID を埋め込む。** 分類 prefix の直後に置く

### リポジトリ全体で一意

**同一のテスト ID を 2 つ以上のケースに割り当ててはならない。** テスト種別が違っても同じ制約がかかる。
ID だけでテストを一意に特定できることを、この規則の目的とする。

同一対象を複数のレイヤで検証する場合は、後発レイヤの prefix にサフィックスを付ける。

| レイヤ      | prefix のサフィックス | 例                |
| ----------- | --------------------- | ----------------- |
| unit        | なし（基準）          | `T-CFG-GI-03-01`  |
| integration | `I`                   | `T-CFG-GII-03-01` |
| functional  | `F`                   | `T-CFG-GIF-03-01` |

ドキュメントコメントから他ファイルのテスト ID を参照するのは構わない。
ここでいう「割り当て」とは、ケース名に書かれた ID だけを指す。

### スコープの名前空間

第 1 セグメントはモジュール・機能の単位、第 2 セグメント以降はテスト対象を表す。
対象セグメントは、ファイル単位ではなくテスト対象の関数・クラス単位で決める。
複数のファイルが同じ prefix を共有してよい。禁止するのは完全 ID の重複だけとする。
共有する場合は連番帯を互いに重ねない。

`init` の直後に、このプロジェクトの名前空間を記入する。

| 名前空間 | 対象 |
| -------- | ---- |
|          |      |
|          |      |

記入例:

| 名前空間  | 対象                           |
| --------- | ------------------------------ |
| `T-LIB-*` | 共有ライブラリのユーティリティ |
| `T-CFG-*` | 設定クラス                     |
| `T-CLI-*` | コマンドライン入力の解析       |

新しい prefix を導入する前に、未使用であることを確認する。

```bash
grep -rl "T-<新 prefix>-" <テストファイルの検索条件> .
```

## 6. テスト ID 重複の機械検査

prefix 一覧や ID 台帳を人手で維持してはならない。実体から導出する。
この原則は [ドキュメントモデル](deckrd-rule-document-model.md) の重複検出と同じ考え方に従う。
本節はテストケース ID 固有の注意点だけを定める。

```bash
# 1) ケース宣言に割り当てられた ID を抽出する
grep -rho '<ケース宣言のパターン>' <テストファイルの検索条件> .   | tr -c 'A-Za-z0-9-' '
'   | grep -xE 'T-[A-Z0-9]+(-[A-Z0-9]+)*-[0-9]{2}(-[0-9]{2})?'   | sort > <一時ファイル>

# 2) 抽出件数を確認する
wc -l < <一時ファイル>

# 3) 2 回以上割り当てられている ID を報告する
uniq -d < <一時ファイル>
```

`wc -l` が妥当な件数を示したうえで、`uniq -d` の出力が空であること。
**件数の確認は省略してはならない。** これは次の 2 つを検知するために行う。

- 0 件 → パイプラインが途中で壊れている
- 想定より極端に少ない → 出力が途中で打ち切られている
  （コマンドプロキシは大量ヒット時に出力を切り詰めることがある。切り詰めを知らせる行は
  後段の `grep` で捨てられるため、件数を見ないと気づけない）

標準エラー出力を捨ててはならない。握り潰すと「重複なし」と区別が付かなくなる。

次の 3 点を外すと、検出漏れ・誤検出を起こす。

- 抽出対象をケース宣言の行に限定する。限定しないと、コメント中の相互参照を割り当てと誤認する
- トークン境界で照合する（区切り文字で分割してから完全一致させる）。しないと、
  prefix 付き ID の内部一致を prefix なしの ID と誤認する
- ファイル単位で一意化してから集計しない。同一ファイル内の重複を取りこぼす。
  割り当ての出現回数を、全ファイル横断で数える

重複が報告されたら、その ID で再検索して割り当て箇所を特定する。

## 7. テストファイルの構成順序

テストファイルは、区切りコメントで示した 5 セクションを決まった順序で並べる。
グループ間は空行 1 行で区切る。

| 順序 | セクション   | 内容                                                 |
| ---- | ------------ | ---------------------------------------------------- |
| 1    | テスト基盤   | テストフレームワーク・アサーション・モックの取り込み |
| 2    | テスト対象   | テスト対象の関数・クラス・定数の取り込み             |
| 3    | ヘルパー     | 検証に必要な補助関数・共有ライブラリの取り込み       |
| 4    | 内部ヘルパー | このファイル内でのみ使う定数・型・関数・スタブの定義 |
| 5    | テスト本体   | テストグループの定義                                 |

- セクション 1〜3 は、言語の取り込み構文（import 相当）をこの順に並べる
- 型・定数・スタブが混在する場合は、1 行コメントを付けたサブブロックに分ける
- セクション 4 は `定数` / `型` / `関数` のサブブロックに分ける
- 不要なセクション・サブブロックは省略してよい

```text
--- テスト基盤 ---
  アサーション / テストグループ・ケース定義 / モック

--- テスト対象 ---
  テスト対象の関数・クラス

--- ヘルパー ---
  補助関数
  # 定数
  # 型

--- 内部ヘルパー ---
  # 定数
  # 型
  # 関数

--- テスト本体 ---
  group "..."
```

## 8. 内部ヘルパーのドキュメントコメント

内部ヘルパーのシンボルには、言語のドキュメントコメント記法で説明を付ける。
何のためのヘルパーかが分からないと、既存ヘルパーが再実装される。

| 対象         | 分量                                      | 記載内容                             |
| ------------ | ----------------------------------------- | ------------------------------------ |
| 定数・スタブ | 1 行                                      | 値の意味と、どのケースで使うか       |
| 関数         | 複数行（引数・戻り値を明記）              | 役割、前提となる状態、引数、戻り値   |
| クラス       | 本体・コンストラクタ・各メソッドの 3 箇所 | 何を差し替えるモックか、各操作の結果 |

テストグループにもドキュメントコメントを付ける。

| 階層 | 分量   | 記載内容                               |
| ---- | ------ | -------------------------------------- |
| 対象 | 複数行 | 対象の責務、割り当てたテスト ID の範囲 |
| 機能 | 複数行 | 機能の責務、検証するシナリオの概要     |
| 分類 | 1 行   | その分類が何を指すか（省略可）         |

## 9. テストファイル名

```text
<テスト対象名>.<テスト種別>.<テストファイルの拡張子>
```

テスト種別は次の 5 つを使う。

| テスト種別  | 検証する範囲                 |
| ----------- | ---------------------------- |
| unit        | 単一の関数・クラス           |
| functional  | 機能単位の振る舞い           |
| integration | 複数モジュールの結合         |
| e2e         | 入口から出口までの一連の流れ |
| system      | 実行環境を含めた全体         |

```text
period-filter.unit.spec.<ext>
parse-session.functional.spec.<ext>
find-sessions.integration.spec.<ext>
main.e2e.spec.<ext>
```

テスト種別ごとの配置場所は、プロジェクトの慣習に従う。

## Common Rationalizations

| 言い訳                                   | 反論                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------ |
| 1 ケースにまとめた方がテストが速く書ける | 失敗時にどの振る舞いが壊れたか分からず、デバッグ時間が書いた時間を上回る |
| ループはケースの中でも動く               | 動くが、最初の失敗で止まり残りのケースが検証されない。網羅性が失われる   |
| テストデータは使う場所の近くが読みやすい | 同じデータが複数箇所に複製され、片方だけ更新されて静かに乖離する         |
| テスト ID は後からまとめて振ればよい     | 後から振ると既存 ID との衝突検査をやり直すことになる。書いた時点で振る   |
| 重複検査は `uniq -d` が空なら合格        | 抽出が 0 件でも空になる。件数を見ないと合格と故障を区別できない          |

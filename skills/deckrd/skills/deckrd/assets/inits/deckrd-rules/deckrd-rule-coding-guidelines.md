## Deckrd Rule: コーディング規約（共通）

言語は問わない。以下のコード例は擬似コードであり、各言語の同等構文に読み替えること。

## 基本方針

- 正しさ > 速さ：動くコードより正しいコードを優先する
- 最小変更：依頼された範囲のみ変更し、不要なリファクタや改善を加えない
- 推測せず確認：既存コードを読んでから提案・変更する

## ライブラリ優先原則

コードを書く前に以下の順序で既存の実装を調べ、使えるものを必ず使う。

1. **共通ライブラリ**（プロジェクト内の shared / utils / libs 相当）
2. **モジュール専用ライブラリ**（対象モジュール内の既存実装）
3. **外部モジュール**（言語標準ライブラリ・登録済み依存）

調査なしに独自実装を始めてはならない。既存関数・定数で対応できる場合はそれを使う。

### インラインロジック禁止

既存関数で表現できる処理を、呼び出し元でインラインロジックとして直書きしてはならない。

```text
Bad — getFilename() が存在するのにインラインで書く
  filename = last_segment(split(normalize_path(file_path), "/"))

Good — 既存の getFilename() を使う
  filename = get_filename(file_path)
```

この原則は文字列操作・配列操作・パス操作など、汎用ユーティリティとして切り出せる
すべての処理に適用する。

## 簡潔なコード

- 同じことをより少ないコードで書けるなら、そちらを選ぶ
- 3 行以上になる処理が既存関数で 1 行に書けるなら、既存関数を使う
- 冗長な中間変数・不要な型キャスト・自明な条件分岐は書かない
- 条件が単純な場合は早期 return を使い、ネストを浅く保つ

## 関数型プログラミング優先

- ループを使わない：配列・コレクションの操作は `map` / `filter` / `reduce` / `flat_map` 等の
  高階関数（言語の同等機能）を使う
- データ変換パイプラインは関数の合成（チェーン）で表現する
- 副作用を持つ処理（I/O・状態変更）はループの外に切り出し、純粋な変換と分離する
- ループが必要になる場合は、まず高階関数で代替できないかを検討してから書く

```text
Bad
  results = []
  for item in items:
    if item.active:
      results.append(transform(item))

Good
  results = items.filter(is_active).map(transform)
```

非同期処理でも同様に、逐次待ちのループより並列実行を優先する。

```text
Bad — 1 件ずつ待つ
  for file in files:
    await process(file)

Good — 並列実行可能な場合
  await all(files.map(process))
```

言語に高階関数の相当機能がない場合（素の Bash など）は、この節は適用しない。
その場合もループ本体を小さく保ち、副作用と変換を分離する原則は維持する。

## 共通の型・定数の配置

複数のモジュールが参照する型・定数を、実装ファイルに直書きしてはならない。
共有ライブラリの下に、型・定数・ユーティリティ関数・クラスを種別ごとのディレクトリに
分けて集約し、実装ファイルはそこから取り込む。

```text
Bad — 同じ型・定数が実装ファイルごとに定義される
  module-a/exporter        ExportConfig 型と DEFAULT_TIMEOUT を定義
  module-b/importer        同じ形の型と同じ値の定数を再定義

Good — 共有ライブラリに 1 箇所だけ置く
  shared/types             ExportConfig
  shared/constants         DEFAULT_TIMEOUT
  module-a/exporter        shared から取り込む
  module-b/importer        shared から取り込む
```

これは「ライブラリ優先原則」の探索順（共有ライブラリ → モジュール専用 → 外部）を
定義側から支える。共有ライブラリに置かれていない定義は探索で見つからず、
再実装を誘発する。

既存の取り込み元を壊さずに移動する場合は、移動元から再公開して互換性を保ってよい。

## 内部シンボルの命名

**そのスコープの外から参照されないシンボルは、外部公開シンボルと区別できる名前にする。**

区別の付け方は言語の慣習に従う（先頭アンダースコア、`private` 修飾子、非 export 等）。

| 区別を付ける対象                                     | 区別を付けない対象                      |
| ---------------------------------------------------- | --------------------------------------- |
| モジュール内部の関数・クラス・定数（外部公開しない） | 関数パラメータ                          |
| 関数内で主要な役割を持つ変数                         | イテレーション変数・コールバック引数    |
| 外部プロセスの入出力を保持する変数                   | setup / teardown スコープで共有する変数 |
| ドメイン概念を表す変数                               | —                                       |

依存注入する関数型・インターフェースには `Provider` 相当のサフィックスを付け、
注入点であることを名前から分かるようにする。

テストファイル内の内部ヘルパーにも同じ規約を適用する
（[Testing Guidelines](deckrd-rule-testing-guidelines.md) 参照）。

## エラーハンドリング

- fail-first 原則：エラーは握りつぶさず、早期に throw / return error する
- 回復不可能な異常（ファイル不在・読み取り失敗・不正入力）はエラーを送出する
- フォールバック値（デフォルト値）を返して処理を続行しない
- 例外は「呼び出し元が期待する正常系」と明確に区別できる場合のみ許容する
  - 許容例：空設定ファイル（定義なしとして扱う）、オプショナルな設定の省略

## Common Rationalizations

| 言い訳                               | 反論                                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------------------- |
| 動いているから触らない               | 読みにくいコードは、壊れたときの修正コストが跳ね上がる                                   |
| この抽象化は将来役立つかもしれない   | 使われていない抽象化は価値のない複雑さ。必要になってから足す                             |
| ついでにこの無関係なコードも直す     | 差分が汚れ、レビュー・切り戻しが困難になる。範囲を守る                                   |
| この型はこのモジュールでしか使わない | 「今は」でしかない。2 箇所目が現れたとき、片方だけ更新されて静かに乖離する               |
| 内部かどうかは読めば分かる           | 読まなければ分からない名前は、外部から呼んでよいかの判断を毎回コードリーディングに変える |

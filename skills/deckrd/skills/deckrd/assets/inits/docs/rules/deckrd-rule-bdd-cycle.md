## Deckrd Rule: BDD 開発サイクル（RGR サイクル）

## 適用トリガー

以下のいずれかの作業をする場合、必ず BDD RGR サイクルを実施する。

| 作業種別         | 例                                       |
| ---------------- | ---------------------------------------- |
| 新機能追加       | 新しい関数・クラス・モジュールの実装     |
| バグ修正         | 既存ロジックの誤りを正す変更             |
| リファクタリング | 外部仕様を変えずに内部構造を整理する変更 |

## 免除条件

以下の変更は RGR サイクルの対象外とする。

- `.md` ファイル・docstring・コメントのみの変更（ドキュメント変更）
- 設定ファイルのみの変更
- フォーマッタによる純粋なフォーマット整形
- 自動生成ファイルの更新

### ファイル移動の特例

内容変更を伴わない純粋なファイル移動は、フル RGR ではなく次の手順でよい。

1. ファイルを移動し、import パスを修正する
2. 全ユニットテストを実行してデグレがないことを確認する

**移動に伴いロジックを変更した場合は、その変更箇所に通常の RGR サイクルを適用する。**

## RGR サイクルの手順

各フェーズの終わりに必ずテストを実行し、次のフェーズへ進む条件を満たしたことを
確認する。テストを実行せずに複数フェーズをまたいで進めてはならない。

| フェーズ | 実施内容         | 次フェーズへ進む条件                     |
| -------- | ---------------- | ---------------------------------------- |
| Red      | テストを書く     | テストが FAIL することを確認した         |
| Green    | 最小実装をする   | テストが PASS することを確認した         |
| Refactor | コードを整理する | テストが引き続き PASS することを確認した |

### Phase 1: Red（テスト先行）

1. テスト対象の関数・クラスのインターフェース（シグネチャ）を確定する
2. プロジェクトのテスト規約に従いテストファイルを作成する
   （構造は [Testing Guidelines](deckrd-rule-testing-guidelines.md) に従う）
3. テストが失敗することを確認する（実装が存在しないか、期待値と異なること）

### Phase 2: Green（最小実装）

1. テストをパスさせる最小限のコードを実装する
   - この段階では「正しい設計」より「テストを通す」ことを優先する
   - 一時的なハードコード等は次のフェーズで解消する
2. すべてのテストがパスすることを確認する

### Phase 3: Refactor（整理）

1. テストを壊さずにコードを整理する
   - [Coding Guidelines](deckrd-rule-coding-guidelines.md) の規約に準拠させる
   - ハードコーディングされている値を型・定数に置き換える
   - 重複ロジックを抽出する
2. フォーマットを確認・修正する
3. 全テストが引き続きパスすることを確認する

テスト・フォーマットの実行経路は [Runners](deckrd-rule-runners.md) に従う。

## BDD 実装エージェント

**BDD RGR サイクルが必要な作業は、必ず `bdd-coder` エージェントに委譲する。**

- Claude Code のメインスレッドで直接コードを書かない
- ファイル移動・import パス変更（ファイル移動の特例）も同様に `bdd-coder` を使う

### エージェント呼び出しのタイミング

| 状況                                              | 対応                               |
| ------------------------------------------------- | ---------------------------------- |
| 新機能・バグ修正・リファクタリングの実装開始時    | `bdd-coder` エージェントを起動する |
| ファイル移動に伴う import パス修正が必要な時      | `bdd-coder` エージェントを起動する |
| テストが RED のまま次フェーズに進もうとしている時 | 作業を止めてユーザーに確認する     |

### エージェントへの引き継ぎ情報

`bdd-coder` 起動時は以下を必ずプロンプトに含める。

- 作業種別（新機能／バグ修正／リファクタリング／ファイル移動）
- テスト対象ファイルと関数・クラス名
- 期待する振る舞い（正常系／異常系／エッジケース）
- 既存テストファイルのパス（存在する場合）
- 使用するテストコマンド

### 1 委譲 = 1 タスク

**タスクが複数ある場合、まとめて委譲しない。1 つずつ委譲し、都度検証してから次へ進む。**

- **他タスクを含む資料を渡さない。** チェックリストファイルを渡す場合は、当該タスク分のみを
  記載したファイルにする。1 ファイルに複数タスクが併記されていると、プロンプトで
  「1 件のみ」と指示しても併記された他タスクまで実装される
- **委譲の直後に実際の変更範囲を検証する。** エージェントの自己申告ではなく差分で確認する

  ```bash
  git status --short
  git diff --stat HEAD -- <対象ディレクトリ>
  ```

- 想定外のファイルが変更されていたら、次のタスクを委譲せず、まずユーザーに報告する

**根拠**: エージェントの自己申告と実際の差分は食い違うことがある。渡した資料に他タスクが
併記されていれば、プロンプトで範囲を限定してもその範囲を越えて実装され、報告では
「触っていない」と申告されうる。自己申告を信用せず差分で確認することを前提に運用する。

## Common Rationalizations

| 言い訳                           | 反論                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------- |
| テストは動作確認後にまとめて書く | 後から書いたテストは実装のなぞりであり、期待される振る舞いの証明にならない   |
| シンプルすぎてテスト不要         | シンプルなコードほど後から複雑化する。テストは期待される振る舞いの記録になる |
| 手動で動作確認したから十分       | 手動確認は残らない。次の変更で壊れても気づけない                             |

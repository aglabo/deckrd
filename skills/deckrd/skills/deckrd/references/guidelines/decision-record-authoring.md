## DR 作成ガイドライン

このファイルを Decision Record（DR）の書き方の正本とする。
DR を書く dr-writer（[Role](../roles/dr-writer.md)）も、既存 DR を書き直す dr-refiner（[Role](../roles/dr-refiner.md)）も、DR をレビューする側も、このファイルだけを基準にする。
プロンプトやコマンド定義に規約の本文を複製してはならない。複製は食い違いを生む。

## 1. DR とは何か

DR は「なぜそう決めたか」を長く残すための非規範文書とする。
モジュールごとに `<modulePath>/decision-records.md` 1 本へ追記していく。

DR は何年も後に読み返される。だから、短い期間で変わる情報を置かない。
読み手は「この決定は今も有効か」「なぜ別案ではないのか」「変えたくなったら何を見直すか」を知りたい。

### 他の文書との境界

| 文書                 | 書くもの                         | DR との関係                                        |
| -------------------- | -------------------------------- | -------------------------------------------------- |
| requirements         | システムが持つべき能力（何を）   | DR は要件を言い直さない。要件 ID で指す            |
| specifications       | 振る舞いと制約（どう振る舞うか） | 実現方式の詳細は spec に書く。DR はその選択理由    |
| implementation       | 判断基準・実装単位               | 関数名・変数名・型構造は DR に書かない             |
| tasks / Issue / PR   | 作業・進捗・担当                 | DR に移行計画・進捗・チェックボックスを書かない    |
| `workspaces/` のメモ | 調査結果・下書き                 | 根拠として参照してよい。メモの内容を DR に貼らない |

## 2. DR にするかの判定

次のすべてを満たすときだけ DR にする。

1. システムの振る舞い・構造・制約・運用に影響する
2. 複数の選択肢があり、どれかを選んだ（または「対処しない」を選んだ）
3. 理由を残さないと、後で同じ議論が繰り返される、または誤って覆される

次のものは DR にしない。

- 誤字・言い回しの明確化、文書の整理
- 自明なドメイン制約（選択の余地がないもの）
- まだ決まっていない検討途中のもの（`workspaces/` のメモに置く。決めたら DR にする）

### 粒度

- 関連する決定は 1 本にまとめる（例: 「入力検証の要件をすべて MUST に上げる」で 1 本）
- 1 本に無関係なテーマを同居させない（D-5）
- レビュー 1 回あたりの DR は 1〜5 本が目安。それを大きく超えるなら統合できないか見直す
- 「対処しないと決めた」ことも DR にしてよい。同じ修正案が繰り返し出るのを防げる

## 3. DR の構成

構造は [テンプレート](../../assets/templates/decision-record.template.md) に従う。各セクションの役割は次のとおり。

| セクション                    | 必須 | 役割                                                                                           |
| ----------------------------- | ---- | ---------------------------------------------------------------------------------------------- |
| 見出し `## DR-NN: <題>`       | ○    | 決定を一文で表す題。「〜とする」「〜を採用する」など、決定内容が分かる形にする                 |
| `**Phase**`                   | ○    | 決定したフェーズ（req / spec / impl / tasks / review-harden）                                  |
| `**Status**`                  | ○    | Proposed / Accepted / Deprecated / Partially superseded by DR-NN（範囲） / Superseded by DR-NN |
| `**Supersedes**`              | 任意 | 置き換える DR と範囲（E-1）                                                                    |
| `### Context`                 | ○    | このプロジェクトで実際に起きている問題、制約、なぜ今決めるのか                                 |
| `### Decision`                | ○    | 決めたこと。言い切る。複数あれば「決定 1」「決定 2」と番号を付ける                             |
| `### Scope`                   | ○    | 適用範囲と、本 DR で決定しないこと（委譲先つき）                                               |
| `### Alternatives Considered` | ○    | 検討した他の案と、それぞれの不採用理由                                                         |
| `### Rationale`               | ○    | 採用案を選んだ理由。根拠（測定値・資料）を示す                                                 |
| `### Consequences`            | ○    | Positive / Negative / Revisit Trigger                                                          |
| `### Open Questions`          | 任意 | 未確定事項。これがある DR は Proposed のままにする（G-1）                                      |
| `### Related`                 | ○    | 関連する REQ / SPEC / DR の ID                                                                 |

## 4. 規約

各規約に ID と強度を付ける。

- MUST: 満たさなければならない
- SHOULD: 原則として満たす。外すときは理由を説明できること

レビューで指摘するときは、規約 ID を添える（例: 「D-4: 照合方式の詳細は spec へ」）。

### A. 参照と配置

#### A-1 MUST: Issue・PR・チケット番号に説明を任せない

番号は管理システムに依存し、移行や整理で辿れなくなる。番号の先を開かなくても DR 単体で読めるよう、内容そのものを書く。

内容を書いたうえでなら、要件や範囲の出どころを示す識別子として番号を添えてよい。
番号を消すと「何がそれを求めたのか」が曖昧になる場合は、残すほうが意味がはっきりする。
決定のきっかけや出どころになった Issue・PR は、本文で触れたかどうかにかかわらず `### Related` に書く（E-3）。
版の変更の出典は、Change History の Description に書く（例: `Add DR-05: ... (from review #123)`）。

- NG: `#448 の議論により、キャッシュキーはベース名のままとする。`（理由が番号の先にしかない）
- OK: `衝突の前提となる「同名ファイルが別ディレクトリにある」状況は、出力名が sessionId 由来のため発生しない。よって、キャッシュキーはベース名のままとする。`
- OK: `Issue #134 は、本 Action の入力を commit-count 1 つにすることを求めている。`（求めた内容が文中にあり、番号は出どころを示す）

#### A-2 MUST: 1 モジュール 1 ファイル、DR セクションは追記のみ

DR は `<modulePath>/decision-records.md` の最後の DR の後に追記する。
直後に置くのは `## Deleted Decision Records`（あれば）、なければ `## Change History` とする。
既存 DR の本文は書き換えない。例外は E-1 の Status 行の更新だけとする。

#### A-3 MUST: 各 DR セクションは `---` で終える

最後の DR も含め、すべての DR セクションの末尾に区切り線 `---` を置く。
最後の DR と `## Deleted Decision Records`・`## Change History` の間も同じとする。

### B. 参照の指し方

#### B-1 MUST: 行番号で指さない

行番号は編集のたびにずれる。

#### B-2 MUST: 参照先が一意に定まる形で指す

| 参照先            | 書き方                                   |
| ----------------- | ---------------------------------------- |
| 要件              | `REQ-F-003`                              |
| 他の DR           | `DR-07`、部分なら `DR-07 決定 2`         |
| 他モジュールの DR | `<namespace>/<module> DR-03`             |
| 仕様の節          | `specifications.md §<章題>`              |
| コード            | ファイルパスとシンボル名（行番号は不可） |

決定を指すときは、その決定を書いた DR を指す。仕様の節を指すのは、振る舞いの詳細を示すときに限る。
こう指すと、DR から DR へのつながりを追える。

- NG: `食い違いの検査方法は specifications-action.md §4 で定める`（検査方法を決めたのは DR-12）
- OK: `食い違いは静的検査で検出する (DR-12)`

### C. 事実と根拠

#### C-1 MUST: Context はこのプロジェクトの事実を書く

一般論や仮定（「〜すると〜になりうる」）ではなく、実際に起きている問題・制約を書く。
コードや一次資料で確かめた事実だけを書き、推測は推測と明記する。

- NG: `一般に、同じ保管境界に置くと権限の分離が難しくなる。`
- OK: `現在、設定ファイルと認証トークンは同じディレクトリに置かれ、読み取り権限が同じになっている。`

#### C-2 SHOULD: Rationale は根拠で裏付ける

測定値、ベンチマーク、仕様書、他 DR を根拠に示す。根拠が `workspaces/` のメモにあれば、そのパスを示す。
「会議でそう決まった」は根拠ではない。決まった理由を書く。
上限・件数などの数値を決めたときは、数値ごとに根拠を書く。根拠が他の DR にあれば、その DR を指す。

- NG: `上限は 3000 件と 120000 バイトとする。3000 件は GitHub の PR の差分の最大ファイル数に合わせる。`（120000 バイトの根拠が無い）
- OK: 上の文に `120000 バイトは、環境変数 1 つ分の上限（約 131072 バイト）に収めるためである (DR-13)。` を加える

#### C-3 MUST: DR 単体で読めるようにする

他の文書を開かなくても、何が問題で、何を決め、なぜそうしたかが分かること。
参照は補足に使い、理解の前提にしない。

#### C-4 MUST: 列挙は全件か一部かを明示し、主張の範囲を列挙に合わせる

仕様などから項目を写して並べるときは、それが全件か一部かを書く。
「〜と同じものを使う」のような主張は、当てはまる項目だけに範囲を限って書く。

- NG: `エラーの文言は _ca-filter-files と同じものを使う。対象の文言は次の 4 つとする。`（仕様には 5 つ目の文言があり、それは _ca-filter-files に無い）
- OK: `次の 4 つの文言は _ca-filter-files と同じものを使う。本 Action だけの文言は specifications-diff.md §4 の表に定める。`

#### C-5 MUST: DR の中の記述を揃える

同じ対象を挙げる箇所（Decision と Consequences など）で、項目が揃っていなければならない。
食い違ったときは Decision を正とする。

- NG: Decision は `"`・`\`・制御文字を挙げ、Negative は `"` と `\` だけを挙げる

### D. 書く内容と線引き

#### D-1 MUST: 移行計画・進捗・タスク表を書かない

工程表、担当、チケットごとの状態、チェックボックスは DR に置かない。tasks や Issue に置く。
移行について決めたことがあれば、作業手順ではなく制約として書く。

- NG: `- [x] 試験環境へ導入した` / `- [ ] 本番へ導入する`
- OK: `移行期間中は旧形式と新形式の両方を読み取れなければならない。`

#### D-2 MUST: 実装コードを書かない

コード片、関数の実装、設定ファイルの中身を貼らない。必要なら spec / implementation で扱う。

#### D-3 MUST: 適用範囲と「決定しないこと」を書く

`### Scope` に、この決定がどこまで及ぶかと、本 DR では決めないことを書く。
決めないことには委譲先（後続の DR・spec・impl など）を書く。委譲先がまだ無ければ「未定（spec で決める）」のように行き先を示す。

```markdown
### Scope

- 適用範囲: CLI から受け取るすべての入力パス
- 決定しないこと:
  - パスの正規化の具体的な規則 → specifications.md §入力パスの正規化
  - Windows の UNC パスへの対応 → 未定（必要になった時点で DR を追加する）
```

#### D-4 MUST: 実現方式を差し替えても書き換えずに済む粒度で書く

判定の問い: **「決定は保ったまま実装の詳細を変えたとき、DR 本文を書き換える必要があるか」**

書き換えが必要な記述（判定位置、環境変数名、照合方法、型構造など）は、DR ではなく spec / implementation に属する。
DR は選んだ方式と、その理由、方式が満たすべき条件に留める。
決定そのもの（下の例なら「許可リストで制限する」こと）を変えるときは、本文を直さず、新しい DR で Supersede する（E-1）。

- NG: `決定 4: 許可リストは環境変数 ALLOW_HOSTS をカンマ区切りで読み、小文字に正規化してから前方一致で照合する。`
- OK: `決定 4: 接続先は許可リストで制限する。許可リストは利用者が実行時に変更できなければならない。`

#### D-5 SHOULD: 1 DR は 1 テーマにする

関係の薄い決定を 1 本に詰め込まない。同じテーマで複数の決定があるときは「決定 1」「決定 2」と番号を付け、後の DR が部分的に置き換えられるようにする。

#### D-6 MUST: Decision は言い切る

「〜とする」「〜を採用する」「〜しない」と書く。「〜が望ましい」「〜を検討する」は決定ではない。
言い切れないなら、まだ決まっていない（G-1）。

#### D-7 MUST: 代替案ごとに不採用理由を書く

代替案を並べるだけでは、後で「なぜこれではないのか」が分からない。各案の末尾に不採用の理由を書く。
案が 1 つしかなかったときは、「何もしない」を代替案として理由を書く。

- NG: `- エラーで終了する`
- OK: `- エラーで終了する。呼び出し元のワークフローが失敗し、初回コミットのリポジトリで使えなくなるため不採用。`

### E. DR 同士・他文書との整合

#### E-1 MUST: Supersede は双方に記録し、部分置換なら範囲を書く

- 新しい DR: `**Supersedes**: DR-07（決定 2: 入力ディレクトリを拒否する部分）`
- 古い DR（全体を置き換える場合）: Status 行を `Superseded by DR-12` に変える
- 古い DR（一部を置き換える場合）: Status 行を `Partially superseded by DR-12（決定 2）` に変える。
  2 回目以降の部分置換は、既存の記載を残して追記する（例: `Partially superseded by DR-12（決定 2）, DR-15（決定 3）`）。
  最後に残った決定まで置き換えたら `Superseded by DR-12（決定 2）, DR-15（決定 1, 3）` とする

古い DR の Status 行の更新は、追記のみの規則（A-2）の唯一の例外とする。本文は変えない。
旧 DR を失効させてよいのは、新しい DR が `Accepted` のときだけとする。`Proposed` の DR は旧 DR の Status を変えない。
採用済みの方針を破棄するので、版は MAJOR を上げる（[版のルール](../../assets/inits/docs/rules/deckrd-rule-document-versioning.md)）。

#### E-2 MUST: DR-ID を再利用しない

ID は `DR-01` から始まる 2 桁以上の連番とする。削除した DR があっても、その番号は使わない。

DR を削除したときは、Change History の直前に次の表を置き、削除した ID を記録する（削除は MAJOR）。

```markdown
## Deleted Decision Records

| ID    | Title  | Reason |
| ----- | ------ | ------ |
| DR-04 | <旧題> | <理由> |
```

新しい ID は、`## DR-NN` 見出しと `## Deleted Decision Records` 表の ID 列の中で最大の番号 + 1 とする。
それ以外の記述（Change History の文面など）は採番に使わない。

#### E-3 MUST: 関連する ID を、定義しているファイルとともに Related に書く

`### Related` に、この決定が影響する・根拠とする REQ / SPEC / DR の ID を 1 行に 1 つ書く。
要件の追加・変更を伴う決定なら、その要件 ID も書く。

- 各行は、ID の前に、その ID を定義しているファイルを書く。読み手が ID からファイルを探さずに済む
- ファイルはモジュールディレクトリからの相対パスで書く。他モジュールのファイルは `<namespace>/<module>` を前に付ける
- 決定のきっかけや出どころになった GitHub Issue・PR も書く（A-1）。同じリポジトリなら `#<番号>`、別のリポジトリなら `<owner>/<repo>#<番号>` とする

```markdown
### Related

- requirements/requirements.md: REQ-F-003
- specifications/specifications-diff.md: R-DIF-002
- decision-records.md: DR-07
- <namespace>/<module> decision-records.md: DR-03
- GitHub Issue: #134
- GitHub PR: <owner>/<repo>#140
```

#### E-4 MUST: version と Change History を同期する

DR を追加したら、frontmatter の `version` と Change History の行を必ず一緒に更新する。

| 変更                                   | 版    |
| -------------------------------------- | ----- |
| DR の追加                              | MINOR |
| 既存 DR の Supersede・撤回・削除       | MAJOR |
| 既存 DR の言い回しの明確化・根拠の補足 | PATCH |

新規作成したファイルは `1.0.0` のまま上げない。

版は 1 コミットにつき 1 つだけ上げる。コミットしていない版上げがすでにあるときは、新しい行を足さない。
コミット済みの版から 1 回だけ上げ直し、まだコミットしていない行を 1 行にまとめる（[版のルール](../../assets/inits/docs/rules/deckrd-rule-document-versioning.md)）。

- 例: コミット済みは `2.2.0`。refine を 2 回実行しても、版は `2.2.1`、行は `2.2.1` の 1 行とする

PATCH は既存 DR の本文に触れるため、A-2 の例外にあたる。`/deckrd dr --add` は PATCH を行わない。
明確化は、決定・Status・Phase を変えないことを条件に、`/deckrd dr --refine` でのみ行う（[7. refine の規則](#7-refine-の規則)）。

#### E-5 MUST: 参照先の要件・仕様と矛盾しない

DR の記述は、参照している要件・仕様の最新の内容と矛盾してはならない。
DR を書くとき・レビューするときは、参照先の該当箇所を読み、対象・範囲・数値が一致することを確かめる。

- NG: DR は `INPUT_BEFORE_SHA` を「名前だけを比べる」対象に含める。仕様 R-ACT-040 は、この env を静的検査の対象から外している

矛盾を見つけたら、どちらが正しいかをユーザーに確かめる。DR の書き誤りなら言い回しを直す。決定が仕様と違うなら、新しい DR で置き換えるか、仕様を直す。

#### E-6 SHOULD: `based-on` を上流の最新版に合わせる

frontmatter に `based-on: requirements.md vX.Y.Z` があるときは、上流の最新版と一致させる。
上流の版が上がったら、DR の内容が新しい版と合っているかを確かめてから `based-on` を更新する。確かめずに版だけを書き換えない。

### F. 表記と語彙

#### F-1 MUST: 言語の規則に従う

見出し（`### Context` など）とフィールド名（`**Status**` など）は英語で固定する。本文は指定の言語（LANG）で書く。
`ja` の場合、本文は日本語、技術用語は英語のままでよい。1 つのファイルの中で文体（敬体／常体）を揃える。

#### F-2 SHOULD: 陳腐化する情報を書かない

「最終更新日」「現在の担当」「今週中に」のように、時間とともに古くなる情報を書かない。
日付が意味を持つ事実（「2026-07 時点の測定で」）は、事実の一部として書いてよい。

「現行」「現在の」「新」「旧」のように、時点によって指すものが変わる語で状態を呼ばない。
実装が終わると、「現行」は改訂後の状態とも読めてしまう。「改訂前」「改訂後」や版番号で書く。

- NG: `現行の入力 before-sha / after-sha を削除する。`
- OK: `改訂前の入力 before-sha / after-sha を削除する。`

#### F-3 SHOULD: 用語を揃える

requirements / specifications と同じ用語を使う。同じものを別の言葉で呼ばない。

#### F-4 MUST: プロジェクトの文書リントでエラーを出さない

DR は、プロジェクトのフォーマッタと文書リント（markdownlint・textlint など）でエラーが出ない形で書く。

- 文の長さ・行の長さ・文体の上限は、プロジェクトのリント設定に従う
- 定義や参照先を書き足して文が長くなったら、文を分けるか箇条書きにする（H-2・H-3）
- リントを止めるための無効化コメント（`textlint-disable` など）を DR に足してはならない
- dr-writer と dr-refiner は、書き込みの後にプロジェクトのスクリプトでフォーマットとリントを実行し、自分が書いた範囲のエラーを直す。直し方は言い回しの変更に限り、決定の意味を変えない
- リントを直すときは、各文の役割（事実・参照・決定）を変えない。承認された文に無かった決定の言い回し（「〜とする」「〜しなければならない」「MUST」）を新しく作ってはならない
  - NG: `本 Action だけの文言は、仕様の表に定める。` を `本 Action だけの文言は failed to list changed files とする。` に直す（参照が決定に変わる）
  - OK: `本 Action だけの文言 (failed to list changed files) もある。` と `その文言は、仕様の表に定める。` の 2 文に分ける
- 自分が書いた範囲は、`--add` では新しい DR と Change History の新しい行、`--refine` では対象の DR と新しい行とする。それ以外の範囲のエラーは報告だけにする

### G. Accepted にする前の点検

#### G-1 MUST: 未確定事項を残したまま Accepted にしない

`### Open Questions` に項目がある DR は `Proposed` にする。

Proposed の DR を確定するときは、本文を直さない。解決した内容で新しい DR を `Accepted` として追加し、
`**Supersedes**:` で元の Proposed DR を置き換える（E-1）。追記のみの規則を保ったまま、確定までの経緯が残る。

#### G-2 SHOULD: 再検討トリガーを書く

Consequences の `Revisit Trigger` に、どんな事実が現れたらこの DR を見直すかを書く。

- 例: `sessionId を持たないチャットログが現れたら、本 DR を見直す。`

### H. 読みやすさ

DR の読み手は、決定に立ち会っていない人とみなす。何年も後に初めて読む人が、上から一度読めば分かるように書く。

#### H-1 SHOULD: 各セクションの冒頭に結論を書く

Context は問題を、Decision は決定を、Rationale は最大の理由を、最初の 1 文で書く。経緯や前提はその後に置く。

- NG: `当初は設定ファイルで切り替える案もあったが、運用中に変更したいという声があり、検討の結果、環境ごとに許可リストを分ける。`
- OK: `許可リストは環境ごとに分ける。目的は、運用中に接続先を変えられるようにすること。`

#### H-2 SHOULD: 一文一義にする

1 つの文には 1 つの事実か 1 つの判断だけを書く。読点で 3 つ以上の内容をつなぐ文は分ける。

#### H-3 SHOULD: 列挙は箇条書き、比較は表にする

3 つ以上の並列する項目は文の中に並べず、箇条書きにする。複数の案を同じ観点で比べるときは表にする。

#### H-4 SHOULD: 略語と指示語に頼らない

- 略語は、その DR の中の初出で正式名を書く
- 「前述の」「上記」「これ」で別のセクションを指さない。指す対象を名前で書く（C-3）

## 5. AI が書くときに起きやすいことと対策

| 起きやすいこと                                         | 対策                                                     |
| ------------------------------------------------------ | -------------------------------------------------------- |
| 手元の情報（タスク、議論の経緯、実装案）を全部詰め込む | D-1・D-4 で判定し、DR に属さないものは落とす             |
| Context を一般論で書く                                 | C-1。コードや文書で確かめた事実だけを書く                |
| 根拠や代替案を作り話で補う                             | 情報が足りないときは書かずに、足りない点を質問として返す |
| 会話の履歴を勝手に要約して DR にする                   | ユーザーが明示した決定だけを DR にする                   |
| 「〜が望ましい」と曖昧に書く                           | D-6。言い切れないなら Proposed と Open Questions にする  |

## 6. セルフチェックリスト

DR を書いたら、出力する前に次をすべて確かめる。レビューでも同じ表を使う。

## 7. refine の規則

`/deckrd dr --refine` は、既存 DR を本節の範囲でだけ書き直す。refine は A-2（追記のみ）の例外であり、版は PATCH とする（E-4）。

### 7.1 変えてはならないもの

refine の前後で、次の項目は同じでなければならない。1 つでも変わるなら、それは明確化ではなく決定の変更とみなす。

| ID  | 不変の項目                                           | 比べ方                                      |
| --- | ---------------------------------------------------- | ------------------------------------------- |
| R-1 | 見出しの `DR-NN`                                     | 文字列が一致する                            |
| R-2 | `**Phase**` 行・`**Status**` 行・`**Supersedes**` 行 | 行全体が一致する（無い行は無いまま）        |
| R-3 | 「決定 N」の番号と、各決定が定める内容               | 番号の集合が一致し、各決定の意味が同じ      |
| R-4 | Alternatives Considered の案の集合                   | 案を増やさず、減らさない                    |
| R-5 | Related の既存の ID                                  | 削除しない（追加は 7.2 に挙げたものに限る） |
| R-6 | DR の数と順序、`## Deleted Decision Records` の表    | 一致する                                    |
| R-7 | Open Questions の項目                                | 足さず、解決扱いで消さない（G-1）           |

見出しの題（`DR-NN:` 以降）は、決定内容が変わらない言い換えに限って直してよい。

### 7.2 変えてよいもの

- 言い回し、文の分割、セクション内の構成（H の各規約）
- Issue・PR 番号に説明を任せている箇所の書き直し（A-1）。内容を書いたうえで出どころとして添えた番号は消さない
- 行番号参照の置き換え（B-1・B-2）
- 移行計画・進捗・チェックボックスの除去（D-1）。決定に関わる制約は残す
- 用語の統一（F-3）、陳腐化する情報の除去（F-2）
- テンプレートに沿った見出し・フィールド名の英語化と並び替え（F-1）
- Related の各行への、ID を定義しているファイルの付記（E-3）
- その DR の本文か、その DR を名指しする Change History の行にある Issue・PR 番号の、Related への追記（E-3）
- リントのエラーを解消するための言い回しの変更（F-4）
- 区切り線 `---` の補完（A-3）
- 決定を仕様の節で指している箇所の、その決定を書いた DR への置き換え（B-2）
- 同じファイルの他の DR に書かれた根拠への参照の付記（C-2）
- DR の中の食い違いを、Decision に合わせて揃えること（C-5）。Decision 側は変えない
- ユーザーの回答に基づく補足: Scope の「決定しないこと」、代替案の不採用理由、Rationale の根拠、Revisit Trigger

ユーザーの回答なしに、根拠・理由・範囲を作って補ってはならない（5. の「根拠や代替案を作り話で補う」）。

### 7.3 指摘の分類

refine のレビューで出た指摘は、次の 3 つに分ける。

| 分類        | 意味                                                                                                                                                   | 扱い                                                                                                          |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `rewrite`   | 7.2 の範囲で直せる                                                                                                                                     | 書き直す                                                                                                      |
| `ask`       | 直すには DR に無い情報が要る（D-3・D-7・C-2・G-2 の欠落など）。または、DR が参照先と矛盾していて、どちらが正しいか DR だけでは決められない（E-5・C-4） | ユーザーに質問する。DR の書き誤りという回答なら 7.2 の範囲で直す。決定が違うという回答なら `supersede` に移す |
| `supersede` | 直すと 7.1 の項目が変わる（D-4 の実装詳細が決定に含まれるなど）                                                                                        | 書き換えない。`/deckrd dr --add` で新しい DR を追加し、Supersede するよう報告する                             |

迷ったら `supersede` とする。意味を変えてしまう書き直しより、書き直さないほうを選ぶ。

E-5・C-4 の `ask` には、DR 側と参照先側の両方の該当箇所を引用して添える。

### 7.4 ファイル単位の点検

DR ごとの点検とは別に、ファイル全体について次を確かめる。

- E-6: `based-on` が上流の最新版と一致しているか。一致しなければ報告する。refine は `based-on` を書き換えない（内容の確認が要るため）
- E-4: コミットしていない版上げがあるか。あれば、反映のときに 1 行にまとめる

## コードコメント ガイドライン

このファイルをコードコメントの書き方の正本とする。
既存コメントを書き直す comment-refiner（[Role](../roles/comment-refiner.md)）も、コードをレビューする側も、このファイルだけを基準にする。
プロンプトやコマンド定義に規約の本文を複製してはならない。

出典: [AIにありがちな「イマイチなコードコメント」9パターン](https://qiita.com/jnchito/items/636c519c0b1d347c79b7)（@jnchito）。
本ファイルの C-1〜C-9 は記事の 9 パターンに、C-10 は記事の補足（仕様はテストに書く）に対応する。

## 1. 基本の立場

- 多くの場合、コメントは無いほうがよい。不要なコメントはノイズであり、コードを読みにくくする。
- コメントに書くのは、コードを読んでも分からない「なぜ」だけとする。
- AI の書いたコメントは、それらしく見えても不要か誤りであることが多い。疑って読む。
- 迷ったら削除を選ぶ。ただし「なぜ」が失われて読み手が困る場合は、削除せず書き直す。

## 2. ルール

各ルールには ID を付ける。指摘はこの ID で記録する。

### C-1: コードを読めば分かることを書かない

何をしているかの説明は削除する。読み手の「なぜこうするのか」に答える内容だけを残す。

```ruby
# NG: コードの言い換え
def total_price
  # 単価 x 数量の総和を合計金額として返す
  items.sum { |item| item.unit_price * item.quantity }
end

# OK: コードだけでは分からない理由を書く
def total_price
  # unit_price には小数が含まれることがあるため、to_d を呼んで
  # BigDecimal に変換し、丸め誤差を避ける
  items.sum { |item| item.unit_price.to_d * item.quantity }
end
```

### C-2: コメントは説明するコードの直前に置く

関数の概要は定義の直前に、個々の処理の説明はその処理の直前に書く。
処理の説明を定義の直前に置くと、関数全体の説明に読めてしまう。
移動した結果 C-1 に当たるなら、移動ではなく削除する。

```ruby
# NG: 処理の説明が関数の概要に見える
# 疲れていたら何もしない
def play_guitar
  return if tired?
  guitar.play
end
```

### C-3: 変更の経緯を書かない

「〜になった」「以前は〜だった」はコミットメッセージや PR に書く。
読み手には現在の仕様だけを伝える。
例外: 過去の仕様が現在の実装に強く結びついていて、それを知らないと誤って変更してしまう場合は、現在形で理由として書く。

```ruby
# NG
# 自転車に乗るときはヘルメットをかぶることが必須になった
raise NoHelmetError unless rider.with_helmet?
```

### C-4: 呼び出し元のことを呼ばれる側に書かない

関数のコメントには、その関数が何をするか（契約）だけを書く。
「どこから・いつ呼ばれるか」は呼び出し元が増えるたびに古くなる。
呼び出し側の事情は、呼び出し側のコードのコメントへ移す。

```ruby
# NG
# FooController と BarController では…するときに…するので、…する前に課金をキャンセルしておく
def cancel_payment
```

### C-5: コードの名前と同じ用語を使う

コードに出てこない用語を説明なしに使わない。コメントの用語は識別子や値に合わせる。

```ruby
# NG: コードは single_coil を見ているのに、コメントは別の話をしている
# ハムバッカーならノイズが少ないので問題は起きない
use(:noise_suppressor) if guitar.pickup == :single_coil

# OK
# シングルコイルはノイズが多いのでノイズサプレッサーでノイズを抑える
use(:noise_suppressor) if guitar.pickup == :single_coil
```

### C-6: 一通りにしか読めない自然な文にする

読み返して、意味が一通りに決まるかを確かめる。曖昧な係り受けや不自然な言い回しは書き直す。
書き直すと事実の主張が変わる場合は、書き直す前に正しい事実を確認する（推測で書かない）。

```ruby
# NG: 「確定して自動継続を止める」のか「確定も自動継続も止める」のか読み分けられない
# 解約すると仮注文の確定と自動継続を止めるので、仮注文には何もしない
return if draft?
```

### C-7: 一歩踏み込んで、読み手の次の疑問に答える

コメントを読んだ人に「では、なぜ残っているのか」「消してよいのか」という疑問が残るなら、その答えまで書く。

```ruby
# NG: 「では、なぜ残しているのか」が分からない
# このクラスは画面から使われていない
class Attachment < ApplicationRecord

# OK
# 画面上では使われなくなったが、過去に登録されたデータを保持するために
# モデルとテーブルを残している
class Attachment < ApplicationRecord
```

### C-8: 同じ内容を呼び出し側と呼ばれる側の両方に書かない

どちらか一方に絞る。通常は、事情を知っている呼び出し側に残す。

```ruby
class Account < ApplicationRecord
  # アカウントを削除したら課金も取り消す
  after_destroy :cancel_payment

  # NG: 上と同じ説明の重複
  # アカウントを削除したら課金も取り消す
  def cancel_payment
```

### C-9: そのコードの責務の外の話を書かない

下位の層（モデル、ライブラリ関数）に、上位の層（画面、コントローラ、特定のコマンド）の事情を書かない。
書くと、層の間に依存があるように見える。特別な理由があるときだけ例外とする。

```ruby
class Guitar < ApplicationRecord
  # NG: モデルに画面の話
  # 編集画面の…では…に応じて表示を切り替えている
  BODY_TYPES = %w(solid flat_top archtop)
end
```

### C-10: 仕様はコメントではなくテストに書く

「〜したら〜になる」という振る舞いの説明は、テストのケース名で表す。
対応するテストがあればコメントは削除する。テストがなければコメントは残し、テスト追加を提案として報告する（コードやテストは書かない）。

## 3. ドキュメントコメント（shdoc / JSDoc / docstring）

関数の契約を書くタグは、型やシグネチャで表せない言語では情報を持つ。次の基準で扱う。

| 対象                                                        | 扱い                                                          |
| ----------------------------------------------------------- | ------------------------------------------------------------- |
| 引数・戻り値・標準出力・終了コード・例外の契約              | 残す。コードと食い違えば、コードに合わせて直す（C-5）         |
| 関数名をそのまま言い換えた概要（例: `get_user - Get user`） | 削除する（C-1）。契約タグだけを残してよい                     |
| 呼び出し元の列挙（`@see caller`、"Called by ..."）          | 削除する（C-4）                                               |
| 他の関数と同じ説明の重複                                    | 片方を削除する（C-8）                                         |
| `@example`                                                  | 使い方に落とし穴があるときだけ残す。自明な例は削除する（C-1） |
| `@version`・変更履歴・作成日                                | ファイルヘッダの規約で決まっている場合を除き削除する（C-3）   |

## 4. 触れてはならないコメント

次のコメントはルールの対象外とし、変更や削除をしない。

- shebang（`#!`）、エンコーディング宣言
- ライセンス・著作権表記と、プロジェクトのファイルヘッダ規約で決まった行（例: `# src:`、`# @(#)`）
- ツールへの指示: `shellcheck`、`eslint-disable`、`markdownlint`、`textlint`、`cspell`、`prettier-ignore`、`# type: ignore`、`# noqa`、`//go:`、`#[allow]` など
- 生成コードの目印（`Code generated ... DO NOT EDIT` など）
- Issue 番号や URL を伴う `TODO` / `FIXME`（未解決の作業を指すため）。番号のない `TODO` は `ask` とする

## 5. 判定の早見表

| 見つけたもの                 | 対応                 | ルール |
| ---------------------------- | -------------------- | ------ |
| コードの言い換え             | 削除                 | C-1    |
| 処理の説明が定義の直前にある | 移動（または削除）   | C-2    |
| 「〜になった」「以前は」     | 削除（経緯は PR へ） | C-3    |
| 呼び出し元の事情             | 呼び出し側へ移動     | C-4    |
| コードにない用語             | 用語を直す           | C-5    |
| 二通りに読める・不自然な文   | 書き直す             | C-6    |
| 次の疑問が残る               | 理由を補う（要確認） | C-7    |
| 同じ説明が 2 か所            | 片方を削除           | C-8    |
| 上位層の話が下位層にある     | 削除                 | C-9    |
| 振る舞いの説明でテストがある | 削除                 | C-10   |
